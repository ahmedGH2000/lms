# Account and responsive-interface update

This is an update to your existing local installation, not a new-site procedure.
Do not delete volumes, run `down -v`, force-reinstall a site, or replace your `.env`.

## What caused the reported failure

Your log showed `QueryTimeoutError` while creating a User. Frappe's
`ask_pass_update()` was writing the shared `email_user_password` default even when
the value had not changed, which requires a database row lock. A separate long
transaction holding that row can therefore block unrelated signups. A regression
deliberately holding the same row reproduced the failure in the original code.
The patch skips unchanged writes; both signup and instructor creation passed with
that lock held. This does not identify which connection held the lock on your
machine, or eliminate all possible database contention.

The instructor forms also created the account and assigned roles in separate
requests. They now make one permission-checked transaction. Validation errors,
duplicates and server/network failures remain visible inside the form. Empty error
responses no longer break the error handler. Success remains visible, including
guidance when outgoing email is unavailable. Phone layouts stack fields, collapse
navigation earlier, wrap long content and keep dialogs scrollable.

## Update safely

1. Back up the running site first. From your existing project folder:

   ```bash
   docker compose --env-file deploy/.env -f deploy/compose.yaml exec app bash -lc 'cd /home/frappe/work/bench && bench --site nightjar.localhost backup --with-files'
   ```

   If the app is not running, do not reset it to make this command work. Preserve
   its volumes and diagnose startup first. Copy important backups outside the
   container/volume as part of your normal backup process.

2. Stop only the application while updating source:

   ```bash
   docker compose --env-file deploy/.env -f deploy/compose.yaml stop app
   ```

3. Extract the updated archive into a **separate temporary folder**. Merge these
   items into your existing `nightjar-learning` directory, replacing their old
   versions (do not replace the entire project folder):

   - `nightjar_learning/` and `frontend/`
   - `deploy/init.sh`
   - `deploy/apply_upstream_patches.py` and `deploy/patches/`
   - `docs/`, `scripts/`, `tests/` and `README.md`

   Keep `deploy/.env`, your current `deploy/compose.yaml`, `private-media/`, Docker
   volumes, and any unrelated local edits. Review overlapping custom source edits
   before merging. This update does not change Compose services or credentials.

4. From the **existing project directory**, start the app and watch its log:

   ```bash
   docker compose --env-file deploy/.env -f deploy/compose.yaml up -d app
   docker compose --env-file deploy/.env -f deploy/compose.yaml logs -f app
   ```

   The first run applies two checked patches and rebuilds native and custom assets.
   Allow it to finish; do not open the UI while assets are being rebuilt. Wait for
   `[Nightjar] Starting development services` and the web-server ready message.
   Ctrl+C exits the log viewer without stopping the detached app. If patch validation
   reports conflicting edits or a different revision, stop and inspect; do not use
   `git reset --hard` or remove the revision guard.

5. Hard-refresh the browser. Open `/lms/settings/users/new` as Administrator and
   create a test Course Creator. Expect a persistent confirmation or an inline
   explanation—not a silent button. Test `/login#signup` in a private window.

## Enable self-registration

In LMS Settings → Signup Settings, turn **Disable Signup** off and save. Check the
same setting in Website Settings. Configure a working outgoing Email Account
before inviting students. Without it, an account can be created but no password
setup email is sent; the UI now tells you this. Use native user/password-reset
administration after mail is configured. Do not share the Administrator password.

Admin username: `Administrator`. Password: the `ADMIN_PASSWORD` value used at the
original site creation (unless subsequently changed in Frappe). Editing `.env`
does not change an already-created administrator's password.

## Remaining checks

The tests ran on a local native Frappe/MariaDB/Redis runtime and Chromium, not your
Docker host. Docker's changing base-image toolchain, actual SMTP delivery, Safari
and physical-phone behavior still need validation. A synthetic encrypted video
played in Chromium, but longer real-video playback/renewal and other browsers
remain separate checks. The archive is not a claim
that every upstream LMS feature is defect-free. No public service was deployed.
